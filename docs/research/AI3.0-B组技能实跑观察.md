## 优化候选（待对齐）

1. **选型前置。** `cap-web-dev` 当前只说按业务选择资源，模板允许 `APP_RESOURCES` 为空。对工单这类需要跨会话查询的业务，在写数据层前先加载 PostgreSQL Skill 并登记所需资源；项目明确要求 PostgreSQL 时，缺连接应追问，并行完成可独立开发的部分。通用模板继续支持无需数据库的网站。
2. **收紧凭据来源。** PostgreSQL Skill 的参考已区分资源管理员、应用与迁移角色，本轮仍从其他项目取得管理连接。项目应只接受本项目的注入配置，或让用户选择明确授权的开发资源；建库凭据由资源配置端持有，应用和迁移各使用项目专用连接。
3. **同步计划与验收。** 数据库方案变更时同步任务清单。验收核对项目约定的资源是否真实启用，再实测业务写入、应用重启后复读和照片回读，避免通用健康检查通过就被当作数据持久化通过。
4. **减少启动试错。** 初始化参考增加 DSH 的命令参数与编辑前置说明；检查脚手架安装是否适合把固定 pnpm 版本和可写缓存整合到一条命令。
5. **定义每个阶段的完成证据。** 记录选型、资源可用、开发服务、浏览器可访问、关键路径验收的真实状态。浏览器执行端预装测试浏览器，AI3.0 预览入口返回就绪状态及可打开的 URL。扣子案例里，八项任务在初始化前建立并多次更新，数据库和存储经平台资源工具接入，开发预览有独立状态。参考[扣子报修案例技术证据](扣子报修案例-技术证据.md)与[预览取证报告](扣子编程-REA取证报告.md)。
6. **API 主验收，浏览器轻验收。** API 覆盖状态流转、权限拒绝、大屏数据和重启后复读。浏览器只做真实入口可达、窄屏提交及成功反馈、桌面后台能操作的冒烟检查。多轮截图和样式复拍从默认流程移出，按界面评审需要执行。B 组已观察到浏览器准备约 6 分钟，随后多次复拍，也确实发现了提交反馈问题。

## 建议先对齐的范围

下一轮保持同一句需求，先把三个节点做明确：

1. **写数据层前确认资源。** 由项目配置声明所需资源及用途，数据库选型和缺配置状态在第一版计划可见。缺连接时集中追问本项目 dev 配置，界面等不依赖资源的工作继续做。就绪检查核对声明的必需资源，不能靠留空跳过。
2. **开发环境只提供项目授权。** 资源配置端持有实例管理连接并建库，Agent 只拿到本项目的应用和迁移权限。现有项目的 `.env` 不作为新项目的连接来源。正式环境独立配置，留给发布阶段。
3. **以可访问预览和分层测试收尾。** 平台提供浏览器入口和状态。接口验收工单状态、权限、统计与真实资源；浏览器保留少量关键操作，截图评审按需执行。交付报告列出通过、失败、未验证项。
